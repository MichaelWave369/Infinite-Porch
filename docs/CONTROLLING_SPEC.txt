# INFINITE PORCH
## Build a People-Owned Network for Communication, Compute, Storage, AI, and Shared Infrastructure

You are taking ownership of a new engineering project called **Infinite Porch**.

Your job is not to write a proposal, mock up a dashboard, or build a networking demo.

Your job is to **design, implement, test, document, and deliver the complete first production-capable version of a decentralized, people-owned network that allows ordinary computers to voluntarily connect and share services and resources with one another.**

Continue through implementation. Do not stop after architecture or scaffolding.

When something cannot reasonably be completed in the first implementation, create the real interface, tests, documentation, and extension boundary for it rather than inventing fake functionality.

---

# 1. THE IDEA

Infinite Porch should allow ordinary people to install software on their PCs and create an independent logical network between those machines.

The network must support:

- direct peer-to-peer communication
- encrypted identity
- discovery of other authorized peers
- private groups and communities
- messaging
- service discovery
- voluntary compute sharing
- AI/model inference sharing
- storage sharing
- resource-aware task routing
- offline/local-network operation
- Internet-assisted operation
- future Wi-Fi/radio/community-mesh transports
- auditable authorization
- cryptographic receipts and provenance

A person's computer becomes a **Porch Node**.

Several Porch Nodes can form a **Porch**.

Multiple Porches may optionally federate.

There must be **no mandatory central cloud authority**.

The existing Internet may be used as one transport, but it must not be the identity, authority, or service layer.

Infinite Porch is therefore an overlay network capable of running across:

- Ethernet
- LAN
- Wi-Fi
- the public Internet
- VPN-like links
- community wireless
- future radio transports
- future PhiOS-native networking

Transport must be replaceable.

The architecture should survive loss of Internet connectivity whenever reachable peers still have another path between them.

# 2. CORE PHILOSOPHY

The following rules are architectural invariants.

## Sovereignty

Users own their:

- identity
- devices
- data
- models
- compute
- storage
- permissions
- logs
- relationships

## Local First

Prefer:

LOCAL DEVICE  
→ TRUSTED LOCAL PEERS  
→ TRUSTED COMMUNITY  
→ FEDERATED PEERS  
→ OPTIONAL EXTERNAL/CLOUD PROVIDERS

Cloud services must never be required for basic LAN operation.

## Capability ≠ Authority

A node advertising a capability does not automatically receive permission to exercise it.

A model seeing a tool does not mean it may use it.

A peer having GPU resources does not mean another peer may consume them.

A peer being reachable does not mean it is trusted.

All externally meaningful effects require explicit bounded authority.

## Human Authority

Human operators remain the final authority over:

- joining
- sharing
- quotas
- permissions
- storage allocation
- compute allocation
- model exposure
- network relaying
- trust relationships
- persistent agents

## Observable ≠ Trusted

Remote claims are claims until verified.

Never confuse:

- advertised capacity
- measured capacity
- authorized capacity
- consumed capacity

Keep those states separate.

# 5. ADDRESSING

Infinite Porch must have its own logical addressing layer.

Do not make users reason primarily about IP addresses.

Objects should be addressable by cryptographic identifiers such as:

porch://peer/<peer-id>

porch://service/<service-id>

porch://blob/<content-id>

porch://porch/<community-id>

porch://model/<provider>/<model>

Implement a signed service-record system that behaves somewhat like decentralized DNS.

Human aliases may resolve to signed cryptographic records.

Prevent silent alias takeover.

# 7. AUTHORITY SYSTEM

Create a deny-by-default authorization system.

A grant should bind at minimum:

- issuer
- recipient peer
- capability
- resource
- action
- scope
- limits
- creation time
- expiration
- nonce
- optional exact-input digest
- signature

Examples:

A peer may:

- run model llama3.3
- maximum 20 requests/hour
- maximum 4 GB VRAM reservation
- until midnight

Another grant might allow:

- store blobs
- maximum 5 GB
- encrypted only
- replication factor ≤ 2

Another:

- relay Porch traffic
- maximum 10 Mbps
- no general Internet exit traffic

Authorization must be checked immediately before effects occur.

Revocation must work.

Expired grants must fail closed.

- timeout
